# PostgreSQL Docker Volumes and Initialization Scripts

## Running the DevBoard Containers

### PostgreSQL

``` bash
docker run -d --name postgres --network devboard-net \
  -e POSTGRES_USER=devboard \
  -e POSTGRES_PASSWORD=devboard \
  -e POSTGRES_DB=devboard \
  -v fe3d61b5c295623da0c0573c34302e2a3b0d4f6e600d44964332d069211f82b0:/var/lib/postgresql/data \
  -v "$PWD/init/postgres":/docker-entrypoint-initdb.d:ro \
  -p 5432:5432 \
  postgres:16-alpine
```

### Frontend

``` bash
docker run -d --name frontend --network devboard-net \
  -p 8080:4173 \
  devboard-frontend
```

### Backend

``` bash
docker run -d --name backend --network devboard-net \
  -e PORT=8080 \
  -e POSTGRES_URL="postgres://devboard:devboard@postgres:5432/devboard?sslmode=disable" \
  -p 8081:8080 \
  devboard-backend
```

# PostgreSQL Persistent Volume

In the PostgreSQL command:

``` bash
-v fe3d61b5c295623da0c0573c34302e2a3b0d4f6e600d44964332d069211f82b0:/var/lib/postgresql/data
```

`fe3d61b5c295623da0c0573c34302e2a3b0d4f6e600d44964332d069211f82b0` is a
Docker volume created on the host machine.

The PostgreSQL container's data directory:

``` text
/var/lib/postgresql/data
```

is mapped to this Docker volume.

Therefore, the PostgreSQL data generated by the application is stored in
the persistent volume rather than only in the container's writable
layer.

This allows the database data to survive container recreation as long as
the same volume is attached to the new PostgreSQL container.

## Recommended Practice

Instead of manually using an automatically generated volume ID, a better
practice is to create a named Docker volume first:

``` bash
docker volume create <volume_name>
```

Then mount that named volume when running PostgreSQL:

``` bash
docker run -d \
  --name postgres \
  -v <volume_name>:/var/lib/postgresql/data \
  postgres:16-alpine
```

For example:

``` bash
docker volume create postgres_data
```

Then:

``` bash
docker run -d --name postgres --network devboard-net \
  -e POSTGRES_USER=devboard \
  -e POSTGRES_PASSWORD=devboard \
  -e POSTGRES_DB=devboard \
  -v postgres_data:/var/lib/postgresql/data \
  -v "$PWD/init/postgres":/docker-entrypoint-initdb.d:ro \
  -p 5432:5432 \
  postgres:16-alpine
```

Using a named volume makes the configuration easier to understand and
manage.

# Manual Bind Mount

Another approach is to manually map a host directory to PostgreSQL's
data directory:

``` bash
docker run -d --name postgres --network devboard-net \
  -e POSTGRES_USER=devboard \
  -e POSTGRES_PASSWORD=devboard \
  -e POSTGRES_DB=devboard \
  -v "$PWD/init/postgres":/docker-entrypoint-initdb.d:ro \
  -v /home/nishant/tws/docker/volumes/data/devboard/:/var/lib/postgresql/ \
  -p 5432:5432 \
  postgres:16-alpine
```

This is a **bind mount** because a specific host filesystem path is
mapped into the container.

### Difference

``` text
Named volume:
postgres_data
     ↓
Docker manages the storage location

Bind mount:
/home/nishant/.../devboard/
     ↓
User specifies the exact host directory
```

For Docker-managed application data, named volumes are generally easier
to manage. Bind mounts are useful when you specifically need the data to
be accessible at a known host filesystem path.

# PostgreSQL Initialization Scripts

The following mount is different from the persistent database volume:

``` bash
-v "$PWD/init/postgres":/docker-entrypoint-initdb.d:ro
```

This maps the project's PostgreSQL initialization scripts into:

``` text
/docker-entrypoint-initdb.d
```

inside the PostgreSQL container.

For example:

``` text
Project
└── init
    └── postgres
        ├── 01_schema.sql
        └── 02_seed.sql
```

These SQL scripts are used to initialize the PostgreSQL database when
the database data directory is initialized for the first time.

The scripts can create the initial schema and seed data, such as the
initial projects and tasks used by the DevBoard application.

## Initial Data vs User Data

It is important to distinguish between **initial data** and
**user/application data**.

### Initial data

The SQL scripts provide the initial database setup:

``` text
init/postgres/
        ↓
/docker-entrypoint-initdb.d/
        ↓
PostgreSQL initialization
        ↓
Initial schema + seed data
```

This can include the initial projects and tasks required when setting up
the application.

### User data

User-created data is generated after the application is running.

For example, when a user creates a new task in DevBoard:

``` text
User creates task
        ↓
Backend API
        ↓
PostgreSQL
        ↓
/var/lib/postgresql/data
        ↓
Persistent Docker volume
```

The user-created task is **not written back into the SQL initialization
files**.

Instead, it is stored in the PostgreSQL database data directory.

------------------------------------------------------------------------

# Key Concept

The two mounts have different purposes:

``` text
1. Initialization scripts

./init/postgres
        ↓
/docker-entrypoint-initdb.d
        ↓
Initial schema + seed data


2. Persistent database storage

Docker volume
        ↓
/var/lib/postgresql/data
        ↓
Actual PostgreSQL database
        ↓
Projects, tasks, and user-created data
```

Therefore:

> **Initialization scripts create the initial database state, while the
> persistent volume stores the live database state.**

If the PostgreSQL container is recreated with the same persistent
volume, user-created data can be preserved.
